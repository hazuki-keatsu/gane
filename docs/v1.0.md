# Gane 项目文档

## 背景

### 为什么是 Go 语言？

Go 语言自 2009 年由 Google 发布以来，凭借**语法简洁**、原生并发、**性能优秀**、生态繁荣等特性迅速成为云原生、微服务和基础设施软件领域的主流语言。

> 本项目本质上是一个实验性项目，主要目的是为了作者自己的保研或者是就业，因此我选择了一个语法相对现代而且简单的语言作为实验的目标，也就是 Go 语言。

### 现有的局限性

尽管 Go 优势明显，但其官方编译器在以下方面存在不足：

1. 第一个问题也就是上文提到的 STW 问题。并发三色 GC 虽然优化良好，但在内存敏感场景仍会产生不可忽视的 STW 暂停。
2. 由于缺乏激进的自动向量化和循环优化，Go 语言在科学计算、AI 算子等场景远不如 C/Fortran。
3. Go 语言自研编译器后端优化深度有限，难以充分利用现代 CPU 的高级指令集。
4. 而且 Go 语言的运行时依赖操作系统和内存管理，无法在无 OS 或资源受限的环境中运行。

### 目标

保留 Go 的极简和现代的语法，赋予 C++ 级别的底层操控力，为关键软件领域提供无 GC、极致性能的系统级开发体验。

具体路线是先实现一个 **兼容 Go 语法标准**、**剥离原生运行时**、**基于 LLVM 的高性能 AOT 静态编译器**，并在此基础上探索 **JIT 动态编译** 带来的激进优化可能性。

## 路线

### 第一阶段：AOT 静态编译器

- [ ] 语法兼容：支持 Go 语言的完整词法和句法规则，基于 `go/parser` + `go/ast` 实现。
- [ ] 运行时剥离：完全移除 Go 原生 GC、goroutine 调度器、栈扩缩容等运行时组件。
- [ ] LLVM 后端：利用 LLVM 生成高质量的跨平台机器码。
- [ ] 可执行产出：能够将 Go 源码编译为独立的可执行文件，无外部运行时依赖。
- [ ] 内存安全：提供极简的手动内存管理或可选的非托管内存操作。

### 第二阶段：JIT 热点优化

- [ ] 运行时热点检测：在 AOT 代码中插入检测桩，识别高频执行的循环和函数。
- [ ] LLVM JIT 集成：利用 LLVM OrcJIT 在运行时动态生成优化代码。
- [ ] 激进优化策略：实现基于运行期上下文的循环展开、向量化、内联等。
- [ ] 无缝热替换：实现 On-Stack Replacement，让程序从 AOT 代码平滑切换到 JIT 优化代码

## 技术选型

| 阶段 | 选型 | 理由 |
| ---- | ---- | ---- |
| 前端解析 | Rust tree-sitter | 避免使用 `go/parser` 带来的额外绑定的成本 |
| 主程序语言 | Rust | 内存安全、零成本抽象、强大的 LLVM 绑定生态。而且 Rust 语言是我擅长的语言 |
| LLVM 绑定 | Rust 高级绑定 `inkwell` | 提供类型安全的 LLVM API 封装，降低开发难度 |
| JIT 引擎 | *（未定）* | - |
| 构建系统 | Cargo | 使用 `build.rs` 作为 Go 和 Rust 的构建工具 |
| 测试框架 | Rust 原生单元测试和基准测试 `criterion` | 用于功能验证和性能对比 |

## 语言子集定义

为实现 V1.0 可工作版本，明确以下为受支持的语法子集：

### 支持

- 基本类型：int, int8, int16, int32, int64, uint, float32, float64, bool, string, byte, rune
- 复合类型：数组 \[N\]T, 结构体 struct { ... }
- 流程控制：if-else, for (三种形式), switch, break, continue
- 函数：多返回值, 命名返回值, 递归
- 闭包：函数字面量（无捕获或极简捕获）
- 指针：*T, &, unsafe.Pointer
- 类型定义：type MyInt int
- 方法：接收者函数
- 接口：仅支持编译时静态分发（结构体实现接口即自动匹配）
- defer：翻译为作用域结束时的逆序执行链
- 内置函数：len, cap (仅作用于数组)

### 不支持

- `new` / `make`：由于依赖堆分配和 GC，故不支持，使用栈上分配替代。
- `map`：由于依赖哈希表运行时，故不支持，用户自行用数组或者结构体模拟。
- `slice`：由于动态扩容依赖 GC，故不支持，仅支持切片字面量 `[]T{...}` 作为固定大小视图。
- `go func()`：因为需要 goroutine 调度器，故降级为普通函数调用。
- `chan`：因为需要并发运行时，故不支持。
- `reflect`：由于需要运行时类型信息，故不支持。
- 标准库（`fmt`, `net` 等）：由于标准库依赖 GC 和 OS 抽象，故不支持，仅提供自定义 FFI 绑定。

## 核心技术挑战与解决方案

### Go 类型到 LLVM 类型的映射

**挑战**：Go 的类型系统与 LLVM 的类型系统需要精确对应。

| Go | LLVM |
| -- | ---- |
| `int` | `i64` |
| `float64` | `double` |
| `struct { a int; b float64 }` | `%Struct = type { i64, double }` |
| `[4]int` | `[4 x i64]` |
| `func(int) int` | `i64 (i64)*` |
| `interface { F() }` | 转为 vtable 结构体，存储函数指针表和数据指针 |

### Go 无运行时环境下的内存管理

**挑战**：无 GC 意味着必须提供替代方案。

- 方案 A：栈上优先分配，编译时确定所有变量生命周期，无堆分配。（先实现这个）
- 方案 B：提供 `alloc` / `free` 内置函数，映射到 `libc` 的 `malloc` / `free`。
- 方案 C：集成简易的引用计数（RC）或线性类型，由编译器静态检查内存安全。（最终支持）

### 接口（interface）的静态化处理

**挑战**：Go 的接口依赖于运行时类型信息。

在编译时进行全程序分析，确定所有实现了某个接口的类型。接口变量在内存中表示为 `{ void* data, void (*vtable)[] }`，其中 vtable 在编译时生成。这实际上是 C++ 风格的对象模型，完全不需要运行时支持。

## 结语

本项目是一次将 **工业级语言语法**（Go）、**系统级编程语言**（Rust）与 **业界标准编译器基础设施**（LLVM）进行深度融合的探索。它超越了单纯的“写一个编译器”的范畴，本质上是在**重新思考编程语言语法与运行时实现的解耦可能性**。
